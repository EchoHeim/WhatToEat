## 新增「日期提醒」功能（微信小程序 WhatToEat）

需求：按公历/农历设定提醒日期，支持按日/月/年循环，可设提醒内容，支持提前 1 天、3 天提醒。

用户确认的三项决策：
1. 落地方式 = 应用内提醒 + 微信订阅消息推送（云函数 + 定时触发器）
2. 入口位置 = 「我的」页面（未占用第 5 个 tabBar）
3. 不关联菜品，做通用文本提醒

### 新增文件
- `utils/lunar.js` — 1900-2100 农历换算（LUNAR_INFO 位压缩表），公历↔农历互转、闰月、月末收敛
- `utils/reminder.js` — 提醒计算引擎：`occurrencesBetween` / `triggersBetween` / `isTriggerOn` / `nextTrigger` / `describe`
- `utils/subscribe.js` — `wx.requestSubscribeMessage` 封装，模板 ID 常量
- `pages/reminders/*` — 提醒列表（今天 / 未来 7 天 / 更远 / 已关闭分组）
- `pages/reminder-form/*` — 提醒编辑（公历⇄农历、循环、提前提醒多选、时间、实时预览）
- `cloudfunctions/reminderPush/` — 每小时定时触发，扫描 `reminders` 集合下发订阅消息
- `tests/engine.test.js`、`tests/pages.test.js` — Node 直跑回归测试

### 修改文件

### 关键设计约定（后续务必遵守）
- `utils/lunar.js` 与 `utils/reminder.js` 是纯函数，云函数复用同一份；**改完必须复制到 `cloudfunctions/reminderPush/lib/`**。
- 循环语义：每月/每年遇 31 日或农历三十自动收敛到月末；农历闰月基准在无该闰月的年份回退到常规月。
- 微信一次性订阅「授权一次只能推一条」，用 `user_settings.pushQuota` 记账；额度为 0 云函数不下发。
- 云函数时区不保证为 UTC+8，用 `getTimezoneOffset()` 修正后取北京时间。
- 提醒推送可选项，未配置 `TEMPLATE_ID` 时应用内提醒仍完整可用。

### 取证结论（全仓扫描 + 逐项 Read，未改动任何代码）

**引擎正确性复核（重要）**：曾怀疑 `lunarOccurrences` 的 yearly 分支跨年错位，逐日扫描 500 天实测推翻该怀疑 ——
2026 中秋 = 2026-09-25 → 触发 09-22/09-24/09-25；2027 中秋 = 2027-09-15 → 触发 09-12/09-14/09-15，
与理论完全一致。**`SEARCH_HORIZON=400` 与 `lunarOccurrences` 的 `startLunar.year+4` 配合下窗口充足，引擎无 Bug。**

**增长能力全仓 0 命中**：`onShareAppMessage` / `onShareTimeline` / `open-type="share"` / `wx.reportEvent` /
`wx.reportAnalytics` / `wx.login` / `wx.getUserProfile` / `getPhoneNumber` / `open-type="contact"` /
`ad-custom` / `RewardedVideoAd` / `InterstitialAd` / `feedback` —— **全部 0 命中**。

### P0 缺陷：推送配额按 `_openid` 聚合，与一次性订阅语义错配

`cloudfunctions/reminderPush/index.js` 的 `readQuota(openid, cache)` 按 `_openid` 取单条 `user_settings.pushQuota`，
但推送主循环会**连续给同一用户推多条提醒**。用户授权 1 次只换 1 条额度，若该用户有 3 条提醒同小时触发，
则仅第 1 条成功、其余静默跳过 —— 用户授权了却收不到推送，是**直接差评来源**。
属产品设计缺陷而非代码缺陷。修法建议：`pushQuota` 改为 `pushQuotaMap[reminderId]` 按提醒记账。

### 其余问题（均有证据）

1. tabBar 已满 4 项，提醒入口埋在「我的」二级页，核心功能发现成本高
2. 种子菜品仅 8 条（`seedDishes` d1~d8），冷启动即空壳
3. Emoji 当菜品图标，与 `frontend-dev` 的 ANTI-EMOJI POLICY 冲突，且机型渲染差异大
4. 无客服入口、无反馈入口、无隐私政策/用户协议页 → 审核与差评风险
5. 前端直连云数据库（`store.js` 内 `wx.cloud.database()`），无服务端校验

### 架构结论：**现有架构正确，不要重构**

`utils/lunar.js` + `utils/reminder.js` 纯函数引擎、云函数复用同一份副本、本地优先+云端兜底 —— 均已踩在正确路径。
缺的不是「更先进的架构」而是三条增长链路（分享、埋点、内容）+ 一次配额语义修正。

**明确建议不要做**（对照 `fullstack-dev/references/technology-selection.md` 反模式）：
拆微服务、自建后端替换云开发、引入 TypeScript 构建链、上 Redis/消息队列。
依据：源码 217.4 KB、4 个集合、单云函数 149 行，规模远未到需要这些的临界点。
