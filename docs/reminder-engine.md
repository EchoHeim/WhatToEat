# 日期提醒：能力与含义

这个模块和「记一餐」是两条独立的数据线：提醒只负责在某个日子提醒你，不写饮食记录。理解它的关键是把「事件日」和「触发日」分开。

## 一条提醒包含什么

| 字段     | 取值                         | 含义                             |
| -------- | ---------------------------- | -------------------------------- |
| 提醒内容 | 40 字以内                    | 推送时截断到 20 字（模板限制）   |
| 日历     | 公历 / 农历                  | 农历含闰月，范围 1900–2100       |
| 日期     | 公历日期或农历月日           | 叫「基准日」，循环规则以它为锚   |
| 循环     | 不重复 / 每天 / 每月 / 每年  | 见下一节                         |
| 提醒时间 | 精确到分钟，默认 09:00       | 决定推送落在哪个时间窗口         |
| 提前节点 | 当天 / 提前 1 天 / 提前 3 天 | 可多选，至少保留一个             |
| 启用     | 开 / 关                      | 关掉即进「已关闭」，不再参与计算 |

## 四种循环的准确语义

| 循环   | 事件日怎么定                                       | 边界处理                                                                                                    |
| ------ | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 不重复 | 只有基准日一天                                     | 过期后归入「已结束」，不再触发                                                                              |
| 每天   | 从基准日（含当天）起每天一次                       | 提前节点没有意义，表单会隐藏并强制按当天算                                                                  |
| 每月   | 公历取每月同一「日」；农历取每个农历月的同一「日」 | 基准日为 31 日时，遇到只有 30 天的月份收敛到月末；农历遇 29 天的月份同理                                    |
| 每年   | 公历取每年同月同日；农历取每年同一农历月日         | 2 月 29 日在平年收敛到 2 月 28 日；基准是闰月而当年没有该闰月时，回退到同名常规月（「闰二月」按「二月」算） |

## 「提前 N 天」到底改变了什么

提前节点不是「多提醒一次」，而是把一个事件日拆成多个触发日。

举例：事件日为 4 月 10 日，提前节点同时勾了当天、提前 1 天、提前 3 天，会产生 4 月 7 日、4 月 9 日、4 月 10 日三个触发日，每个触发日各算一次、各推一条。列表里「今天」分组是按**触发日**算的，不是按事件日算——所以 4 月 7 日那天打开小程序，这条提醒会出现在「今天」。

推送文案也据此生成：触发日当天是「就是今天」，其余是「还有 N 天」。

## 提醒时间与 5 分钟窗口

定时触发器每 5 分钟跑一轮（cron `0 */5 * * * * *`），云函数只处理「提醒时间落在刚刚过去那个 5 分钟窗口内」的记录：14:30 的提醒会在 14:30–14:34 那一轮命中，14:35 那一轮已经超窗，因此既不重复也不补推。

这条规则带来两个可感知的后果：

- 提醒时间可以精确到分钟，但实际送达有 0–5 分钟延迟
- 关掉小程序期间错过的触发日不会补推，也不会在列表里留一条「逾期」；循环提醒直接跳到下一个触发日

窗口长度（云函数里的 `WINDOW_MINUTES`）必须与 cron 间隔一致。把 cron 改回每小时一次却留着 5 分钟窗口，整点之后的提醒会全部漏掉。

## 去重与推送额度

- 每条提醒记录 `lastPushed`，当天推过就跳过，同一事件日最多一条推送
- **候选靠 `nextTriggerDate` 筛，不再全表扫**：保存提醒时算出「下一次触发日」写进字段，云函数只查 `enabled: true 且 nextTriggerDate <= 今天`。扫描量因此只跟「今天要响的提醒」有关，跟一共攒了多少条无关。推完立刻把该字段推到下一次；没有下一次（单次已过期 / 停用）写哨兵 `9999-12-31`
- 升级前的老提醒没有这个字段，客户端同步时补一次，云函数那边也留了一层兜底（查出缺字段的补上再照常处理）
- 云函数下发前检查用户 `pushQuota > 0`
- 微信「一次性订阅」的规则是**授权一次只能推一条**：用户每完成一次授权 `pushQuota` 加 1，推送成功或收到 `43101`（未订阅 / 额度用尽）后尽力减 1 或清零，额度为 0 时不发消息
- **额度能自动补**：订阅弹窗底部那个「总是保持以上选择，不再询问」，用户勾上之后，同一模板再调 `wx.requestSubscribeMessage` 不会弹窗、直接返回 `accept`，微信侧再记一次订阅（微信小游戏指南把它写成「推送多次消息的方案一」）。所以 `utils/subscribe.js` 挂在一串自然点击上静默补：首页抽签 / 「就吃这个」/ 签到条、记录页保存、签到页「签到」与空态「去签到」、签到表单提交。额度低于 `HIGH_WATER`（60）才补，一小时最多 40 次；**到 60 次就停手，手动点「额度+1」不受这个上限约束**
- **订阅弹窗只在「新建」时出现一次**：新建提醒、新建纪念日保存后各弹一次（这是唯一能让用户勾上「总是保持」的时机）。编辑已有条目不再弹；自动补额度的路径没勾过就完全不调接口，不会打扰
- 判据只有一条：`wx.getSetting({withSubscriptions:true})` 的 `itemSettings` **只包含勾过的模板**，空着就是没勾过，不能静默调。状态缓存在 `wte_sub_state_v1`，`autoState()` 返回 `accept` / `reject` / `off` / 空，提醒页据此换文案；`reject` 和 `off` 只能引导去 `wx.openSetting`，代码无解
- **必须在 tap 回调里同步发起**，`await` 过一轮网络就出了点击手势，微信报 `can only be invoked by user TAP gesture`。这条模拟器不暴露，只有真机看得见
- 没勾「总是保持」的用户不会自动补，仍走提醒页的「额度+1」显式按钮——这是平台规则，不是实现上的偷懒
- `config.js` 的 `SUBSCRIBE_MODE` 控制是否校验额度：`'once'`（默认）按上面记账；`'longterm'` 是长期订阅，授权一次可长期下发、跳过额度校验，但仅政务民生 / 医疗 / 交通 / 金融 / 教育等线下公共服务类目可申请。工具类、电商类、内容类在公共模板库里只能选一次性订阅

## 应用内提醒与微信推送的边界

- **应用内提醒**：打开小程序就能看到今天该提醒的事，零配置，不依赖云函数
- **微信推送**：需要模板 + 云函数 + 触发器 + 用户授权四件事全部就位。小程序不支持后台本地推送，没有模板时就只有应用内提醒
